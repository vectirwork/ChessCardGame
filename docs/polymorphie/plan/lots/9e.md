# Lot 9e : Changer un réglage ne casse que les gardes prévus

## Objectif
Aujourd'hui, changer une seule valeur par défaut fait échouer de 9 à 101 tests (docs/REGLAGES.md, section 2 ; essais
du lot 9c dans …/scratchpad/poly/lots/9c/resultats2/*.json et le script …/lots/9c/essais2.sh). Ce lot rend les tests
indépendants des valeurs par défaut, pour qu'un développeur qui change un réglage ne voie échouer QUE les gardes
voulus, chacun avec un message qui dit quoi mettre à jour :
- test/garde-fous/defauts.test.ts (photographie des défauts : reporter la valeur dans defauts.json) ;
- test/garde-fous/protocole.test.ts (monter PROTOCOL_VERSION et mettre à jour test/fixtures/protocole.json) ;
- test/reglages-doc.test.ts (reporter la valeur dans docs/REGLAGES.md) ;
- et checkRules qui refuse un réglage impossible (6 cartes : la construction s'arrête, c'est voulu).
Il fournit aussi un outil pour essayer un réglage sans toucher au dépôt, et règle quelques reliquats.

## Fichiers possédés
- test/** (sauf test/fixtures/v1/** : témoins figés, n'y touche pas)
- scripts/** (nouveau scripts/essai-reglage.mjs ; scripts/verifier-lot.mjs)
- package.json (script npm de l'outil)
- docs/REGLAGES.md, docs/polymorphie/ETAT.md, README.md (section des commandes)
- src/shared/config/brand.ts, src/shared/config/timings.ts (commentaires ou raccord, identique au défaut)
- src/shared/pgn.ts et src/client/storageKeys.ts seulement pour lire BRAND.pgnVariant / BRAND.storagePrefix (identique
  au défaut, site construit identique ; sinon, ne les touche pas et présente ces deux champs comme des rappels)
- Code source : AUCUNE autre modification, sauf un export ajouté pour qu'un test puisse fixer ses règles (comportement
  et site construit identiques).

## Étapes
1. Outil d'essai : scripts/essai-reglage.mjs (+ script npm « essai-reglage »). Il copie le dépôt suivi par git
   (git ls-files -co --exclude-standard) dans un dossier temporaire, y lie node_modules, applique un ou plusieurs
   remplacements exacts dans des fichiers (option répétable `--remplacer=<fichier>::<texte avant>::<texte après>`, refus
   si le texte avant n'apparaît pas exactement une fois), puis lance tsc, `vitest run --project rapide` (rapport JSON),
   et `npm run build` avec `--build`. Il affiche les tests en échec groupés par fichier, en séparant les GARDES
   ATTENDUS (liste ci-dessus) des AUTRES, et sort en code 0 seulement s'il n'y a aucun « autre » échec. Il nettoie le
   dossier temporaire (sauf `--garder`). Prévois des raccourcis pour les essais courants (`--essai=cinq`,
   `deuxParTour`, `remplaceCoup`, `presage4`, `trente`, `mur`, `six`) qui reprennent exactement les essais du lot 9c.
2. Découplage, fichier par fichier, en partant des échecs des essais (lessons, climats, accueil, pouvoirs-adverse,
   climats-adverse, server-regles, puzzles, v2-correction, pgn, marque, compat-parties, game, climats-random,
   frequences, server-config, server-clock, server-features, socle-client, config, textes-regles, server-draft) :
   - un test qui vérifie le moteur ou une page AUX RÈGLES V1 les fixe explicitement (createGame(…, { rules: RULES_V1 }),
     setRulesOverride dans le test avec remise à zéro, ou règles passées en paramètre) : il teste alors la même chose
     quel que soit le défaut ;
   - un test qui vérifie qu'un texte ou une valeur SUIT le réglage calcule l'attendu à partir du réglage (pour la valeur
     d'aujourd'hui, l'attendu doit rester la chaîne exacte : garde la chaîne exacte quand le réglage vaut la valeur
     V1, et une forme dérivée sinon) ;
   - un test qui vérifie le contenu (leçons, problèmes) tient compte des contenus masqués par `requires` ;
   - n'affaiblis rien au défaut : chaque assertion d'aujourd'hui reste vérifiée à l'identique quand le réglage vaut sa
     valeur V1 ; ne supprime aucun test ; ne marque rien comme sauté ; le nombre de tests au défaut ne baisse pas.
   - Si un test doit vraiment échouer quand un réglage change (photographie voulue), déplace la photographie dans un
     des gardes voulus avec un message clair, ou fais-en un nouveau garde explicite listé par l'outil.
3. Vérifie avec l'outil les 7 essais : seuls les gardes attendus échouent (et la construction s'arrête pour `six`).
   Donne le tableau avant / après (nombre d'échecs « autres »). Vérifie aussi `npm run temoins` : il compare aux
   témoins v1 et peut échouer après un changement de défaut ; dis ce qu'il fait dans chaque essai et documente-le.
4. Reliquats :
   - scripts/verifier-lot.mjs : la fin d'un gel (`jusqua`) est comparée par égalité (ligne ≈ 132). Calcule le rang de
     chaque lot d'après carte.vagues et ne refuse que si rang(apres) < rang(lot) < rang(jusqua) ; un lot de la vague de
     `jusqua` ou plus tard n'est plus gelé. Test du calcul (test/verifier-lot.test.ts si besoin).
   - test/garde-fous/defauts.test.ts : corriger le commentaire qui dit que les autres tests passent quand un réglage
     change (il devient vrai après ce lot : dis-le précisément).
   - config/timings.ts : le commentaire de BOT_TIMEOUT_MS dit que le navigateur le lit ; seul le serveur le lit (le
     client garde WORKER_TIMEOUT, src/client/ai/index.ts) : corrige le commentaire.
   - config/brand.ts : BRAND.pgnVariant et BRAND.storagePrefix ne sont lus nulle part ; relie-les au code (pgn.ts,
     storageKeys.ts) si c'est sans effet sur le site construit au défaut (vérifie les empreintes de dist/ et la taille
     du paquet principal), sinon présente-les comme des rappels dans leur commentaire et dans REGLAGES.md.
5. docs/REGLAGES.md, section 2 : remplace le tableau d'échecs par celui d'après ce lot, présente l'outil
   (`npm run essai-reglage -- --essai=cinq`, `--remplacer=…`) et simplifie l'étape 3 en conséquence. README : la
   commande. ETAT.md : une ligne dans le rapport final.
6. Contrôles : tsc ; npx vitest run (tout vert, nombre de tests au défaut ≥ celui d'avant) ; npm run temoins ; npm run
   build et empreintes de dist/ identiques à celles d'avant le lot (sauf si BRAND est relié et que tu prouves que seul
   ce qui doit changer change — au défaut, rien ne doit changer) ; node scripts/verifier-lot.mjs 9e. Aucune mesure de
   performance.
